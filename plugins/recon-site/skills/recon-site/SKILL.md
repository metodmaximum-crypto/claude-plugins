# Разведка структуры сайта

Реализует Этап 02 регламента агентства. На выходе — структура сайта, каждую
страницу которой можно обосновать данными, и файл разведки для защиты КП.

**Это работа для продажи, до подписания договора.** Ориентир по объёму —
экспресс, а не полный сбор семантики. Сезонность, сотни запросов и глубокий
разбор — после подписания, в Стадии 1.

## Настройка

Ключи лежат **вне папки скилла** — в `~/.recon-site/.env`
(Windows: `%USERPROFILE%\.recon-site\.env`). При установке плагином папка
скилла заменяется на каждом обновлении, и ключи рядом со скриптами пропали бы.
Образец — `.env.example`. Другой путь можно задать переменной `RECON_SITE_ENV`.

Пути `scripts/…` и `references/…` — относительно папки скилла.
Зависимостей нет: только стандартная библиотека Python 3.

Проверка доступа к Яндексу: `python scripts/check_access.py "фраза" <ID региона>`.
Без ключей работают `site_audit.py` и `competitor.py`.

## Железное правило

> Цифры спроса и позиции выдачи не берутся из головы. Только из вывода
> инструмента, с датой замера и ссылкой на файл-сырьё.

Если инструмент не отработал — страница получает пометку `гипотеза`, а не
выдуманное число. Регламент это прямо разрешает (раздел «Если данных нет»).
Придуманная цифра хуже отсутствия разведки: КП выглядит обоснованным и
разваливается на защите.

## Два режима

Режим задаётся **отдельно для каждого источника**, не глобально. Обычная
рабочая конфигурация — Яндекс по API, Google через браузер.

| | `api` | `browser` |
|---|---|---|
| Как работает | HTTP-запросы к API | Claude in Chrome на залогиненной сессии пользователя |
| Присмотр | не нужен | нужен: капчи, подтверждение региона |
| Скорость | минуты | десятки минут |
| Когда выбирать | есть ключ | ключа нет, или API не отдаёт нужное |

В режиме `browser` работать только через **Claude in Chrome** — там уже есть
сессии пользователя. Встроенный браузер не подходит: вводить пароли нельзя.

**Капчу не решать.** Появилась — остановиться, сказать пользователю, дождаться,
продолжить с чекпоинта. Чекпоинт писать после каждого запроса.

## Источники данных

| Что нужно | Яндекс | Google |
|---|---|---|
| Спрос | Search API Wordstat (`scripts/wordstat.py`) | Keyword Planner — **только браузер**, аккаунт Google Ads |
| Выдача | Search API (`scripts/serp.py --engine yandex`) | `--engine google-cse`, либо браузер |
| Аудит сайта | `scripts/site_audit.py` — ключи не нужны | PageSpeed Insights API |
| Конкуренты | `scripts/competitor.py` — ключи не нужны | то же |

Три оговорки, которые надо знать заранее:

- **Google Custom Search JSON API — это не реальная выдача.** Другой индекс,
  нет локального пака, порядок отличается. Для вопроса «кто в топ-5 по запросу
  с геолокацией» он не годится. Нужна настоящая выдача — только браузер или
  платный сторонний провайдер.
- **Keyword Planner без активных трат отдаёт диапазоны** («1К–10К»), а не
  точные числа. Это не поломка, так и фиксировать: `1К–10К`.
- **Wordstat не поддерживает операторы** (`!`, `+`, `[]`). Для экспресса это
  ровно то, что нужно: базовый запрос уже включает свои уточнения.

## География спроса ≠ география бизнеса

Регламент говорит «регион клиента» и молча предполагает, что клиенты ищут
оттуда же, где бизнес. Для туризма, экспорта, B2B на выезд это ломается.

Перед снятием спроса определить, **откуда ищут**, и снимать срезы раздельно:

| Срез | Кто ищет | Где мерить |
|---|---|---|
| Предтрип | планирует из дома, до поездки | Яндекс + Google, регион страны происхождения |
| В-маркете | уже на месте, ищет с телефона | Google, локация места, язык места |

Срезы **не складывать и не усреднять** — это разные люди с разным намерением
и разными конкурентами. В структуре сайта они дают разные страницы.

Признак, что случай именно такой: услуга оказывается в одной стране, а
покупатель живёт в другой. Тогда же проверить язык: есть ли версии под каждую
аудиторию, стоит ли `hreflang`.

### Откуда физически уходит запрос

У Google локация берётся из двух мест, и важно понимать, из какого именно:

- **Место названо в запросе** («аренда авто пхукет») — Google трактует запрос
  по этому месту и прямо пишет об этом над выдачей. Снимать можно откуда
  угодно, органика будет по делу. Чужими останутся только реклама и локальный
  пак — их в этом случае не засчитывать.
- **Места в запросе нет** («аренда авто рядом», «car rental») — локацию
  подставляет IP. Параметр `gl` его не переопределяет, `uule` надёжно тоже.
  Снимать можно только из нужной страны.

Второй случай — это ровно запросы в-маркете: человек уже на месте и название
места не пишет. Поэтому без машины в нужной стране этот срез не покрывается,
и в файле разведки он помечается как непокрытый, а не подменяется первым.

Проверено: среда исполнения скилла уходит через Франкфурт.

`serp.py` печатает страну выхода, пишет её в артефакт и по каждому запросу
отмечает, откуда взялась география. При несовпадении с `--expect-country`:
запросы с географией — предупреждение, запросы без неё — стоп. Перечень
географических слов задаётся `--geo-terms`.

**Яндекса это не касается:** Search API принимает регион параметром и считает
его на своей стороне. Ещё один довод в пользу режима `api` там, где он есть.

## Алгоритм

Шаги повторяют регламент. Шаг 7 остаётся человеку.

1. **Вводные.** Из ссылки на сайт — ниша и тип; из описания проекта — то же
   словами. Определить географию спроса (см. выше) и язык(и).
   **Регион подтверждает человек** — ошибка тут тихая и дорогая.
2. **Аудит текущего сайта** — `site_audit.py`. Нет сайта → шаг пропустить и
   пометить в файле разведки. Это нормальный путь, а не ущербный.
3. **Спрос** — 10–30 **базовых** запросов на срез. Длинные хвосты не брать:
   базовый запрос уже включает уточнения, иначе спрос посчитается дважды.
   Список запросов показать человеку до прогона.
4. **Выдача** — 5–10 продающих запросов на срез. Записать топ-10, посчитать
   долю агрегаторов (`references/aggregators.md`), выделить настоящих
   конкурентов. Отличать локального игрока от федеральной или международной
   сети с городской посадочной — `competitor.py` это проверяет.
5. **Структуры 2–3 лидеров** — `competitor.py`. Пометить: что берём, что у них
   лишнее, чего у них нет.
6. **Сборка структуры** — по `references/categories.md`. Каждой странице:
   уровень, тип У/Т/С, ядро/масштаб, раздел, название, что на странице, зачем
   нужна, обоснование.
7. **Проверка на бизнес-логику — человек.** Путь до заявки, интеграции,
   пожелания клиента. Агент только готовит чек-лист.

Затем — **верификатор**: отдельным проходом проверить результат по
`references/readiness.md`, не заглядывая в собственные рассуждения.

## Выход

```
<клиент>/razvedka/
  00-vvodnye.json        ниша, гео спроса, язык, тип сайта
  01-audit.json          находки по текущему сайту
  02-wordstat.json       запрос → показов + дата замера   (чекпоинт)
  03-serp.json           топ-10 + метка агрегатор/сервис/сайт
  04-konkurenty.json     разделы лидеров
  struktura.tsv          → лист «0. Структура сайта» калькулятора
  fail-razvedki.md       конкуренты, выводы, аргументы для защиты КП
```

Колонки `struktura.tsv` — строго по листу «0. Структура сайта»: Уровень ·
У/Т/С · Ядро/Масштаб · Раздел · Название страницы · Что на странице · Зачем
нужна · Обоснование.

Каждое обоснование ссылается на файл-сырьё, чтобы на защите КП можно было
ткнуть пальцем, откуда цифра.

## Чего не делать

- Не собирать полную семантику — это Стадия 1, после подписания.
- Не копировать структуру лидера целиком: у него могут быть разделы под его
  бизнес-модель (опт, франшиза, история).
- Не строить структуру со слов клиента без данных — хотелки идут в бриф.
- Не оставлять страницу без «зачем». Не формулируется одной фразой — в ядре
  ей не место.
- Не смешивать срезы спроса разной географии.
